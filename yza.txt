━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

In firebase_auth_service.dart, signInWithGoogle() uses Supabase OAuth:

    supa.OAuthProvider.google,

The OAuth flow opens a browser, user signs in, browser redirects back to app.
The ACTUAL session arrives later via onAuthStateChange — NOT from the return

In firebase_app_state.dart:

  if (result.user != null) {      // ← ALWAYS false for OAuth

So FirebaseAppState.signInWithGoogle() ALWAYS returns an error, even when
Google sign-in actually succeeds.

Back in enhanced_login_screen.dart:

  if (error != null && mounted) {
    // _showErrorSnackBar('Failed to sign in: $error');  ← COMMENTED OUT
  } else if (mounted) {
    Navigator.of(context).pushReplacement(AuthWrapper()); // Never reached
  }

error is ALWAYS not null  →  the navigation block NEVER runs.
The snackbar is commented out  →  the user sees NO feedback at all.

The user clicks their Google account, the OAuth flow completes in the browser,
they return to the app — but the app does nothing and the user stays on the
login screen.

================================================================================
WHAT IS ACTUALLY HAPPENING
================================================================================

There are two separate stores for session data:

  1. In-memory  →  FirebaseAppState._sessions  (List<CommunicationSession>)
  2. On-disk    →  Hive box via LocalSessionService

ON SIGN-OUT:
  _clearUserData() sets _sessions = []  (in-memory cleared)
  LocalSessionService is NOT touched    (Hive data survives sign-out ✓)

ON SIGN-IN:
  _loadUserData() runs:
    Step A  →  loads from REMOTE  (network call, takes 1-3 seconds)
    Step B  →  saves remote data to Hive

  During Step A (while network call is pending):
    _sessions is still []  (cleared by _clearUserData())
    notifyListeners() has not fired yet
    AuthWrapper shows HomeScreen (user is set, onboarding is set)

  HomeScreen, InsightsDashboard, and SessionHistoryScreen._syncFromRemote()
  all call appState.getRecentSessions() which reads _sessions:

    List<CommunicationSession> get sessions => _sessions;

    List<CommunicationSession> getRecentSessions({int limit = 10}) =>
        _sessions.take(limit).toList();

  So these three screens see an EMPTY list for 1-3 seconds after every sign-in.
  The user sees blank cards / zeroed stats / empty history until the remote
  call finishes — it looks like their data was deleted.

The Hive data on disk is perfectly intact — it just isn't being read first.

================================================================================
SHOULD _clearUserData() BE REMOVED OR CHANGED?
================================================================================
Short answer: NO. Keep it exactly as-is.
================================================================================


WHERE IT IS CALLED
──────────────────────────────────────────────────────────────────────────────
_clearUserData() is called from three places:

  1. Auth state listener (line 192)
       when user == null  →  user just signed out
       _clearUserData() is correct here

  2. deleteAccount() (line 435)
       after the account is deleted from Supabase
       _clearUserData() is correct here

  3. clearAllData() (line 853)
       utility method for full wipe (used for debugging / account removal)
       _clearUserData() is correct here


WHAT _clearUserData() CLEARS
──────────────────────────────────────────────────────────────────────────────
  _user = null               ← MUST clear — auth identity is user-specific
  _relationshipData = null   ← MUST clear — relationship belongs to this user
  _sessions = []             ← see analysis below
  _currentSession = null     ← MUST clear — active call must end on sign-out
  _currentSessionId = null   ← MUST clear — same reason
  _isOnboardingComplete = false  ← MUST clear — onboarding state is per-user
  _currentUserId = null      ← MUST clear — Partner A/B role is per-user


THE _sessions = [] LINE — WHY IT IS CORRECT TO KEEP IT
──────────────────────────────────────────────────────────────────────────────
The concern is: "clearing _sessions deletes the user's data."

It does NOT delete data. It clears the in-memory pointer. The data lives
in two places:

  1. Supabase (remote)         — always safe, not touched by _clearUserData()
  2. Hive on disk (local)      — NOT touched by _clearUserData() either

_sessions = [] only clears the List<CommunicationSession> held in RAM.
The moment the user signs back in, _loadUserData() (with the Hive fix)
repopulates _sessions from Hive instantly — before any screen even renders.

So the user NEVER sees blank data because of _sessions = []:
  • At sign-out: user is on the login screen — no sessions screen visible
  • At next sign-in: Hive loads into _sessions BEFORE HomeScreen renders

Keeping _sessions = [] on sign-out is also the CORRECT thing to do for
privacy: if a different person signs in on the same device, they must not
see the previous user's sessions in memory.


WHAT WOULD BREAK IF YOU REMOVED _clearUserData() or _sessions = []
──────────────────────────────────────────────────────────────────────────────
  • Removing _clearUserData() entirely:
    Auth state listener would not clear user/relationship/session on sign-out.
    AuthWrapper would see appState.user still set even after sign-out.
    The Consumer would never navigate to login screen. App breaks completely.

  • Removing only _sessions = [] from _clearUserData():
    In memory, the previous user's sessions remain after sign-out.
    If a second person signs in on the same device, they briefly see the
    first person's sessions (privacy leak) until _loadUserData() overwrites
    them from remote.
    Not catastrophic for a single-user device, but wrong.


VERDICT
──────────────────────────────────────────────────────────────────────────────
  _clearUserData() — keep it, every line is correct and necessary.
  _sessions = []  — keep it, the Hive fix already solves instant data display.

  The "data disappearing on sign-out" concern is fully solved by the Hive
  cache-first strategy in _loadUserData() documented above. No changes to
  _clearUserData() are needed or recommended.

ISSUE 5 — RETRY ANALYSIS WIDGET APPEARING FREQUENTLY
================================================================================

SYMPTOM
──────────────────────────────────────────────────────────────────────────────
After submitting partner ratings, the user lands on CallAiAnalysisScreen.
Instead of AI insights loading successfully, the "Analysis unavailable" /
"Retry analysis" error widget frequently appears, requiring a manual retry.
Often the retry itself succeeds — meaning the data and server are fine but
the first attempt consistently fails.


FILES INVOLVED
──────────────────────────────────────────────────────────────────────────────
  lib/screens/resolution/call_ai_analysis_screen.dart  — UI + error state
  lib/services/session_analysis_loader.dart            — orchestration logic
  lib/services/call_analysis_service.dart              — HTTP layer / timeout
  lib/models/call_analysis_result.dart                 — response model


PIPELINE OVERVIEW (what happens on every first-load)
──────────────────────────────────────────────────────────────────────────────
  1. CallAiAnalysisScreen.initState() calls _runAnalysis() after first frame.
  2. _runAnalysis() calls SessionAnalysisLoader.loadOrAnalyze().
  3. loadOrAnalyze() does:
       a. appState.refreshRelationshipFromServer()       ← STEP A (Firestore)
       b. _fromAppState() — check in-memory cache        ← STEP B
       c. _sessionsService.getSessionAiAnalysis()         ← STEP C (Firestore)
       d. Check pendingCallAudioPath is non-null/exists   ← STEP D
       e. callAnalysisService.analyzeCall()               ← STEP E (HTTP + STT + Gemini)
       f. sessionsService.saveCallAnalysis()              ← STEP F (Firestore)
  4. Any throw at any step surfaces in _runAnalysis()'s catch block as
     setState(() { _error = e.toString(); _loading = false; })
     → retry widget appears.


ROOT CAUSE 1 — 120-SECOND TIMEOUT IS TOO TIGHT FOR THE FULL PIPELINE
──────────────────────────────────────────────────────────────────────────────
Location: lib/services/call_analysis_service.dart line 11

  static const Duration _timeout = Duration(seconds: 120);

This 120-second budget is applied to the ENTIRE HTTP request — which includes:
  • Serializing and uploading the audio file (size ∝ call duration)
  • Server-side STT transcription (depends on audio length, model latency)
  • Gemini AI analysis call (variable, typically 10–30s)
  • Streaming the response back to the client

For a 10–15 minute call on a 4G connection, audio upload alone can take
60–90s. The remaining 30–60s is too little for STT + Gemini, so the request
hits the 120s wall and Flutter throws a TimeoutException, which propagates
directly to _error → retry widget.

This is the most common cause of the "frequently" pattern — the retry
succeeds because the second attempt may hit a faster server process or the
audio is already in a server cache.

FIX: Increase _timeout to Duration(seconds: 300) (5 minutes). Audio upload +
STT + Gemini analysis can legitimately take 3–4 minutes for longer calls.
Alternatively, use a two-step approach: upload audio first (separate endpoint),
then trigger analysis (separate endpoint), each with their own timeout.


ROOT CAUSE 2 — NO RETRY LOGIC IN THE SERVICE LAYER
──────────────────────────────────────────────────────────────────────────────
Location: lib/services/call_analysis_service.dart — analyzeCall()

analyzeCall() makes exactly ONE HTTP attempt. Any transient failure —
momentary network drop, server overload spike, DNS hiccup — throws
immediately with no retry. The caller (session_analysis_loader.dart) also
has no retry logic. So every transient error becomes a user-visible retry
prompt, even though a silent automatic retry would have succeeded.

FIX: Add a simple retry loop in analyzeCall() — 2 automatic attempts with
a 3-second delay between them for transient errors (TimeoutException,
SocketException, HTTP 5xx). Only throw to the caller on final failure.

Example shape:
  int attempts = 0;
  while (true) {
    try {
      final streamed = await request.send().timeout(_timeout);
      final response = await http.Response.fromStream(streamed);
      return _parseResponse(response);
    } catch (e) {
      if (++attempts >= 2 || e is CallAnalysisException) rethrow;
      await Future.delayed(const Duration(seconds: 3));
    }
  }

CallAnalysisException (non-200 server response) should not be retried
because the server already rejected the request intentionally.


ROOT CAUSE 3 — refreshRelationshipFromServer() BLOCKING AT THE START
──────────────────────────────────────────────────────────────────────────────
Location: lib/services/session_analysis_loader.dart line 39

  await appState.refreshRelationshipFromServer();

This is the very first thing loadOrAnalyze() does, before even checking the
in-memory or Firestore cache. If the user's Firestore connection is slow or
times out (no explicit timeout set on this call), the analysis never starts.
The exception propagates directly to _error → retry widget.

Additionally, this network call is unnecessary when the analysis is already
cached in memory (_fromAppState() at line 41 would return immediately) or
in Firestore (line 48). The refresh is only needed when fresh partner data
is required for the actual Gemini analysis step.

FIX: Move refreshRelationshipFromServer() to AFTER the cache checks:

  // Check in-memory cache first (no network needed)
  final cached = _fromAppState(appState, sessionId);

HARD BLOCKER — Supabase client SDK cannot delete users
  File: lib/services/firebase_auth_service.dart

  File: lib/providers/firebase_app_state.dart — deleteAccount() method

  in-memory state (_sessions = [], _user = null, etc.). But

    app.post('/api/user/delete', async (req, res) => {
      try {
        // 1. Extract Bearer token from Authorization header
        const authHeader = req.headers['authorization'];
        if (!authHeader || !authHeader.startsWith('Bearer ')) {
          return res.status(401).json({ success: false, message: 'Missing auth token' });
        }
        const token = authHeader.split(' ')[1];

        // 2. Verify token and get user identity (uses anon client, not admin)
        const { data: { user }, error: verifyError } =
          await supabaseAnon.auth.getUser(token);

        if (verifyError || !user) {
          return res.status(401).json({ success: false, message: 'Invalid or expired token' });
        }

        // 3. Delete user via admin SDK
        const { error: deleteError } = await supabaseAdmin.auth.admin.deleteUser(user.id);
        if (deleteError) {
          console.error('Admin delete failed:', deleteError);
          return res.status(500).json({ success: false, message: deleteError.message });
        }

        console.log('User deleted:', user.id);
        return res.json({ success: true });
      } catch (err) {
        console.error('Unexpected error in /api/user/delete:', err);
        return res.status(500).json({ success: false, message: 'Internal server error' });
      }
    });

  Note: supabaseAnon is your existing Supabase client (with the anon key, used
  to verify the user's JWT). supabaseAdmin is the new one with the service role
  key (used only to call auth.admin.deleteUser). If your backend only has one
  client, you can verify the JWT manually with jsonwebtoken, or just pass the
  user's ID in the request body and verify with the anon client as shown.

  The endpoint can be POST (simplest) or DELETE — either works. The Flutter
  side will use POST to match this example.
